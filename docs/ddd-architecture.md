# 아키텍처와 도메인 경계

- 검사기의 범용 허용 범위를 앱에 임의로 적용하지 않는다.
- 코드 작성은 [품질 지침](code-quality.md), 실행은 [개발 지침](development.md#실행과-검증), 검사기 변경은 [유지보수 지침](quality-maintenance.md)을 따른다.

## 새 기능을 분류하는 절차

**업무 사실 → BC → 불변식·생명주기 → 어그리게이트 → 트랜잭션·패키지** 순서로 판단한다.

- **BC:** 업무 모델과 용어가 같은 뜻으로 통하는 범위. 업무 목적·의미·결정 책임·변경 이유로 정한다. 결정 책임은 실제 사람·개발팀 수가 아니라 규칙과 용어를 정하는 권한이다.
- **어그리게이트:** 한 루트가 소유한 상태의 일관성을 지키는 단위. 불변식·소유 관계·독립 생명주기·동시 변경으로 정한다. 한 BC에 여러 어그리게이트, 한 어그리게이트에 여러 엔티티·값 객체가 있을 수 있다.

개념의 근거는 [Evans의 DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)와 [Fowler의 Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)를 따른다. 아래 업무 전제·배치·절차는 이 템플릿의 선택이다.

1. **명령·조회와 업무 규칙을 적는다.** 누가 무엇을 바꾸고 어떤 결과·실패·동시 요청을 허용하는지 확인한다. 클래스·테이블·API·화면 개수나 함께 읽는다는 사실로 경계를 추측하지 않는다.
2. **기존 BC부터 확인한다.** 같은 의미·결정 책임을 유지하면 기존 BC를 쓴다. 독립된 목적·모델이 필요한 구체적 이유가 있을 때 새 BC를 검토한다. 같은 단어의 의미 충돌은 증거지만 필수조건은 아니다. 다른 소비자·담당자·개발팀·향후 확장 가능성만으로 분리하거나 합치지 않는다.
3. **조회에 필요한 사실을 확인한다.** 이미 저장된 사실이면 기존 조회 또는 애플리케이션 모델·조회용 `Store`를 쓴다. 여러 루트의 조회가 새 루트를 뜻하지 않는다. 취소 시각처럼 없는 사실은 소유 모델에 기록하는 변경도 필요하다. 월별 집계가 접수일·취소일 중 무엇을 기준으로 하는지 모르면 질문한다.
4. **상태의 소유와 생명주기를 확인한다.** 기존 루트와 함께 존재하거나 그 불변식에 속하면 필드·값·자식 엔티티로 추가한다. 독립 생성·변경·종료와 자기 규칙이 있으면 같은 BC의 새 어그리게이트를 검토한다. 자식 ID만으로 분리하지 않는다. 큰 컬렉션·무제한 이력·잠금 경합은 소유·보존 요구부터 재검토한다.
5. **읽기·쓰기·판정 시점·실패 계약을 정한다.** 여러 루트의 원자적 쓰기가 필요하면 불변식과 경계를 재검토하고 이유·잠금·롤백 계약을 기록한다. 한 트랜잭션이 필요하다고 BC·루트를 자동 병합하거나 연동 요구만으로 비동기 전달을 추가하지 않는다.
6. **코드·등록 목록·행동 테스트에 반영한다.** 경계를 바꾸는 요구라면 이전 선택을 덮어쓰지 않고 변경 이유를 남긴다.

확정된 사실로 판단 가능한 부분은 구현한다. **결과를 바꾸는 업무 사실이 빠졌을 때만 질문**한다. 기존 BC에도 맞지 않고 새 모델도 불명확하면 배치를 보류한다. 기존 BC·공용 도메인을 임시 수용소로 쓰지 않는다. 별도 모델이 확인된 CRUD는 새 BC, 기존 모델의 CRUD 확장은 기존 BC, 업무 모델이 없는 기술 연결은 `config`·어댑터에 둔다.

BC가 정해져도 루트의 소유·생명주기가 미정이면 루트와 테이블은 확정하지 않는다. 예를 들어 점검 업무에 장비 ID가 등장해도 이 시스템이 장비를 생성·관리하는지 모르면 Equipment 루트를 만들지 않는다.

### 변경 설명에 남길 최소 기록

모든 변경은 위 절차로 소유 루트·불변식·실패·일관성 영향을 검토하고 [자동 검사와 완료 조건](#자동-검사와-완료-조건)을 충족한다. 소유 루트·선택 근거·검증할 규칙·실패·동시 실행 계약을 남기고, 새 BC·어그리게이트 또는 생명주기·일관성·연동 계약 변경에는 다음 항목을 모두 기록한다.

```text
요구와 확정된 업무 사실:
소유 BC와 선택 근거:
루트·소유 상태·불변식·독립 생명주기:
읽는 것 / 쓰는 것 / 판정 시점·실패 계약:
분류 결과와 채택하지 않은 대안의 이유:
변경할 패키지·경계 목록·행동 테스트:
불명확한 사실과 필요한 질문:
```

### 분류 사례

- **기존 루트:** 문서에 새 블록 종류를 더하면 블록 수·ID 유일성과 리비전 규칙을 Document에서 함께 지킨다. 블록 저장소를 만들지 않는다.
- **자식 엔티티:** 스레드 안의 댓글은 개별 ID로 고치고 지워도 CommentThread가 소유하고 상태 규칙을 함께 지키므로 그 안의 엔티티로 둔다.
- **같은 BC의 새 루트:** 문서 템플릿을 스페이스마다 따로 만들고 고친다면 Document를 바꾸지 않는 독립 ID·생명주기이므로 `workspace`에 새 루트를 검토하고 SpaceId로 참조한다.
- **새 BC:** 외부 저장소와의 양방향 동기화처럼 자기 상태·재시도·결정 책임이 생기면 별도 모델로 분류한다. 테이블이 더 필요하다는 이유로 나누지 않는다.
- **조회:** 스페이스별 문서 수는 `workspace` 조회 모델(`Store`·`Catalog`)이다. 새 루트를 만들지 않는다.
- **스페이스별 권한:** 멤버 초대는 스페이스마다 역할을 주는 일이라 팀 BC를 만들지 않고 `access`의 SpaceMembership 루트로 두었다. 로그인 허용과 요청자 판정을 `access`가 이미 소유하기 때문이다. 조직 단위 관리가 요구되면 그때 다시 분류한다.

## 업무 규칙

### Agent Docs

소유자 한 사람이 운영하는 문서 서비스다. 사람은 웹에서, 에이전트는 MCP·REST로 같은 문서를 읽고 고치고 댓글로 주고받는다. `access`는 누가 들어오고 에이전트가 어디까지 할 수 있는지를, `workspace`는 문서 내용·이력·댓글을 결정한다. `webhook`은 소유자가 등록한 수신처로 문서·댓글 이벤트를 서명해 보내고 재시도한다. 활동 로그는 세 BC가 함께 쓰는 루트 공용 포트(`ActivityReporter`·`ActivityCatalog`)이고, 지금 요청한 사람이 누구인지 다시 확인하는 루트 공용 입력 포트 `CurrentCallerUseCase`(`CurrentCallerSnapshot`)를 `access`가 구현한다.

| BC | 루트와 소유 상태 | 규칙 |
| --- | --- | --- |
| `workspace` | Space: `SpaceId`, 주소(`SpaceSlug`)와 예전 주소, 이름·설명, 외부 링크, 보관 시각 | 주소는 소문자·숫자·안쪽 하이픈 1~50자이고 예전 주소 50개까지 예약해 다른 스페이스가 쓰지 못한다. 이름 1~100자, 설명 500자 이하. 로컬 경로 링크는 `/`로 시작하는 절대 경로다. 에이전트가 보내는 작업 디렉터리와 비교하기 때문이다. 만들기·바꾸기·보관은 소유자만. 보관한 스페이스는 스페이스 목록(에이전트의 `spaces_list` 포함)과 스페이스 찾기에서 빠지고, 문서는 그대로 두며 주소로 계속 열리고 권한이 있는 사용자의 전체 검색·제목 찾기에 포함된다. 쓰기를 막지는 않는다. 에이전트 지침 문서는 같은 스페이스의 휴지통 밖 문서만 지정하고, 다른 스페이스 문서와 없는 문서는 같은 오류로 거절한다. 지정은 문서 ID만 남기므로 그 문서를 휴지통에 넣거나 지우거나 다른 스페이스로 옮기면 설정은 남고 읽을 때 안내하지 않는다(`trashed`·`unavailable`). 짧은 GitHub 참조의 기본 레포는 연결한 `github_repository` 링크 중에서만 고르고, 그 링크를 빼면 기본 선택도 지운다. org 링크만으로는 레포를 정하지 않는다. |

**판정 시점:** 문서·스레드·스페이스 주소·인가 요청·리프레시 토큰·업로드 허가의 쓰기는 루트 행을 잠근 뒤 기준 버전(`baseVersion`)·블록 해시·코드 상태를 확인한다. 다르면 아무것도 쓰지 않고 충돌로 실패한다. 블록 편집은 대상 블록 해시만 비교하므로 다른 블록이 바뀌어도 적용한다. 본문 저장·머리 정보 변경(`docs_move` 포함)·복원은 웹·에이전트·REST 모두 기준 버전을 반드시 보낸다. 빠뜨린 요청은 받지 않고, 기준 버전이 현재와 다르면 충돌이며 응답에 현재 버전과 내용을 담는다. 충돌 판단에 리비전 내용을 쓰지 않는다. 다른 쪽 변경과 합치는 일은 기준을 가진 쪽이 한다([웹 저장](frontend-architecture.md#문서-모델과-편집기-계약)). `opId`가 있는 쓰기를 같은 쓰는 쪽이 같은 `opId`로 다시 보내면 다시 쓰지 않는다. 본문이 없는 REST 쓰기(휴지통 이동·복원, 영구 삭제, 댓글 삭제)는 `opId`를 쿼리 파라미터로 받는다. 다시 보낸 요청은 처음 시도와 같은 접근 검사를 거친 뒤 저장해 둔 처음 응답을 그대로 돌려준다. 그사이 문서·스레드가 바뀌어도 응답은 같다. 바뀐 것이 없던 성공 쓰기도 처음 응답을 기억하고, 실패한 쓰기는 기억하지 않는다. 예외는 처음 응답(`payload`)을 저장하기 전에 기록된 `write_operations` 행뿐이다. 이 행에는 종류·대상·리비전만 있어 처음 응답을 되살릴 수 없으므로, 같은 `opId`가 오면 행을 지우거나 고치지 않고 다시 적용하지도 않은 채 `legacy_operation` 오류로 이미 처리됐음을 알린다. 오류는 지금 접근 검사를 통과했을 때만 기록된 대상과 리비전을 근거로 담고, `fix`는 같은 요청을 새 `opId`로 다시 보내라고 하지 않는다. 현재 문서와 이력에서 처음 요청이 반영됐는지 확인하고 더 바꿀 것이 있을 때만 새 작업을 하라고 안내한다. 삭제는 기억한 응답보다 우선한다. 댓글을 지우거나 문서를 영구 삭제(30일 자동 정리 포함)하는 쓰기는 지운 댓글의 본문·수정 이력이나 지운 문서의 내용을 담은 처음 응답도 함께 버리고, 처리했다는 기록은 남겨 같은 `opId`를 다시 적용하지 않는다. 버린 응답이 있어야 답할 수 있는 재요청은 처음 결과가 지워졌다는 오류로 거절한다. 이 오류는 `legacy_operation`과 구분하고, `fix`는 같은 요청을 새 `opId`로 다시 보내라고 하지 않고 현재 문서와 이력을 확인하라고 안내한다. 정확한 오류 코드는 REST Docs가 원본이다. 처음 응답에 함께 바뀐 문서(`alsoChanged`)가 있으면, 다시 보낸 요청은 주 문서와 그 문서들을 지금도 보고 편집할 수 있을 때만 처음 응답을 돌려준다. 다른 스페이스로 옮겨진 아래 문서의 예전 내용이 새지 않게 하기 위해서다. 리비전 이름·블록 복원·이사·수정 제안 결정·반응·점유도 같은 `opId` 규칙을 따르고, 점유를 다시 보낸 요청은 처음 점유를 돌려줄 뿐 연장하지 않는다.

**스페이스 권한:** 요청자의 권한은 스페이스마다 따로 있다. `access`의 `Caller.spaces`와 루트 공용 `CurrentCallerSnapshot.spaces`는 스페이스 UUID에서 범위(`read < comment < edit`)로 가는 맵이고, `scope`는 그 요청자의 전역 상한이다. 맵이 null인 것은 사람 소유자뿐이다. 맵 값에는 소유자 권한이나 전역 상한을 넘는 값을 넣지 못하며, 소유자의 에이전트도 전역 소유자가 되지 못한다. 맵은 만들 때 복사한 읽기 전용이라 만든 뒤 바뀌지 않는다. 이 복사를 건너뛰는 생성 경로가 없도록 `Caller`·`CurrentCallerSnapshot`·`SpaceScope.Listed`는 값 비교(`copy`·`equals`)를 주는 data class로 두지 않는다. 멤버의 맵은 고정된 멤버십에서 만들고(editor는 edit, commenter는 comment) 전역 상한은 그 가운데 가장 높은 값(없으면 read)이다. 연결의 맵은 허용 스페이스마다 연결 범위다. `workspace` 입력 어댑터가 이 맵을 `SpaceScope.Listed.grants`로 번역하고, `Access.permissionIn(스페이스)`는 그 스페이스 값과 전역 상한 가운데 낮은 값을, 없는 스페이스에는 null을, 사람 소유자에게는 소유자 권한을 준다. 모든 쓰기 검사는 이 값으로 한다. 문서 만들기·편집·이동·이사·복원·블록 복원·리비전 이름·업로드·휴지통 이동과 꺼내기는 그 스페이스의 edit 이상, 영구 삭제는 사람 소유자, 스레드 열기·답글·반응·답변함 표시·다시 열기는 comment 이상이다. 웹 응답의 `permission`은 요청한 사람의 지금 권한이고, 문서 응답이면 그 문서가 지금 있는 스페이스 기준이다. `opId` 재요청은 저장해 둔 처음 결과를 그대로 돌려주되 `permission`만은 저장하지 않고 지금 요청자와 지금 문서 스페이스로 다시 붙인다. 이사 전에 저장된 결과가 예전 스페이스 권한을 말하지 않게 하기 위해서다. 이력 화면의 권한도 지금 문서 기준이고 과거 리비전이 있던 스페이스를 근거로 쓰지 않는다.

**여러 루트 쓰기:** 댓글 쓰기는 스레드와 받은편지함 항목을 한 트랜잭션에 저장한다. 알림 없는 댓글이나 댓글 없는 알림을 남기지 않기 위해서다. 스레드를 열거나 앵커를 옮길 때 그 문서에 확정 전 입력이 있으면 그 입력의 확정도 함께 커밋한다. 앵커가 가리키는 리비전에 지금 대상 글이 없는 상태를 막기 위해서다. 영구 삭제는 문서와 그 문서에만 속한 리비전·스레드·받은편지함 항목을 함께 지우고 첨부는 남긴다. `answering`을 단 문서 편집은 새 리비전과 그 리비전을 스레드에 연결하는 일을 함께 커밋한다. 답한 리비전이 스레드에 없거나 스레드만 답변한 상태로 남지 않기 위해서다. 토큰 교환은 인가 코드 소비와 연결 발급을 함께 커밋한다. 한 코드로 연결이 두 번 생기거나 코드만 소비되고 연결이 없는 상태를 막기 위해서다. 업로드 토큰으로 올린 첨부와 허가의 사용 표시는 함께 커밋한다. 파일 하나만 받고, 저장하지 못한 파일은 허가를 쓰지 않게 하기 위해서다. 수정 제안 수락은 문서 행을 잠근 뒤 스레드 행을 잠그고, 확정 전 입력 확정·범위 적용·새 리비전·제안 결정과 리비전 연결을 함께 커밋한다. 비상 로그인은 허가 소비와 웹 로그인 발급을 함께 커밋한다. GitHub 로그인은 이 로그인의 대기 초대를 잠근 뒤 User 저장과 그 초대들의 사용자 고정을 함께 커밋한다. 고정되지 않은 채 들어오거나, 들어오지 못했는데 초대만 고정되는 상태를 막기 위해서다. 사람 편집 시간의 채택은 여러 EditSession을 한 통계 트랜잭션에서 바꾼다. 한 저장 요청에 숨겨지기 전 전경과 지금 전경처럼 서로 다른 전경 구간의 아직 보내지 않은 입력이 함께 올 수 있는데, 그 저장의 문서·버전과 요청 묶음 ID는 한 번만 채택하기 때문이다. 일부 전경만 반영된 채 채택 표시가 남으면 나머지 입력을 다시 보낼 수 없다. 그래서 모든 구간의 시각·저장 버전을 먼저 검사하고, 전경 범위를 정렬한 순서로 잠근 뒤(만료 처리도 같은 순서로 잠근다) 채택 표시 하나와 범위마다의 채택·닫힌 구간 재결합(`supersededBy`)을 함께 커밋한다. 구간 하나라도 잘못되거나 저장에 실패하면 그 요청의 통계 전체를 버린다. 예외는 세 가지다. 이 트랜잭션은 문서 쓰기와 별개(`REQUIRES_NEW`)라 통계 실패가 이미 커밋된 문서 결과를 되돌리지 않는다. 바뀐 것 없는 저장이나 이미 채택한 묶음은 구간을 바꾸지 않는다. 에이전트 구간은 이 묶음 채택에 들어가지 않는다. 아래 상위 문서·이사 규칙과 이 통계 채택을 빼면 그 밖의 쓰기는 루트 하나만 바꾼다.

**이사:** 문서를 다른 스페이스로 옮기는 쓰기는 출발 문서와 아래 문서, 목적 상위 문서, 스레드·받은편지함 항목, 관련 첨부 행을 잠그고 확정 전 입력 확정, 문서마다 이사 리비전, 스레드·받은편지함 소속 변경, 첨부 이동·사본·바인딩을 한 트랜잭션에 저장한다. 출발·목적 스페이스 모두 편집 권한과 기준 버전이 필요하고, 목적 경로 중 하나라도 쓰이면 아무것도 옮기지 않는다. 문서·블록·표 행열·스레드·댓글 ID와 확정 리비전은 그대로다. 일반 문서·스레드 저장도 참조하는 첨부 행을 잠가 현재 소속을 확인하므로, 묶음만 쓴다고 판정해 옮긴 첨부를 남은 문서가 뒤늦게 참조하면 거절한다. 원래 스페이스의 과거 활동 로그는 지우지 않고 옮긴 뒤의 제목으로 바꿔 보여 주지 않는다.

**한 요청 안의 별도 커밋:** 편집 시간 통계는 문서 쓰기가 커밋된 뒤 따로(`REQUIRES_NEW`) 기록하고, 통계 전용 범위 행으로 같은 주체의 구간을 차례로 쓴다. 한 트랜잭션에 묶으면 통계 실패가 본문을 되돌리기 때문이다. 그 사이 프로세스가 죽으면 그 입력의 통계는 빠질 수 있다. 폴더 가져오기는 트랜잭션 없이(`NOT_SUPPORTED`) 같은 BC의 공개 업로드·문서 생성 유스케이스를 파일마다 부르고 파일별 결과를 돌려준다. 업로드·생성은 각자 커밋되므로 폴더 전체는 원자적이지 않다. 앞서 만든 문서·첨부는 뒤 파일이 실패해도 되돌리지 않고, 문서 생성이 실패하면 올린 첨부만 남을 수 있다. 같은 경로가 둘 오면 둘 다 실패하고 기존 문서를 덮어쓰지 않는다. 내보내기는 사람 소유자만 하고(소유자 권한의 에이전트도 거절) REPEATABLE_READ 읽기 전용 트랜잭션 하나에서 만든다. 확정 전 입력은 확정하지 않고 그대로 담고, 토큰·세션·연결·webhook 비밀은 읽지 않으며, 지운 댓글은 본문·수정 이력 없이 자리만 담는다. webhook 계획은 페이지마다 활성 엔드포인트 행을 잠근 뒤 기존 전달 키를 읽고 빠진 것만 넣는다. 전달은 마감된 전달 행 하나를 잠가 시도를 세는 트랜잭션, 트랜잭션 없는 HTTP 요청, 결과를 적는 트랜잭션으로 나뉘고, 410으로 엔드포인트를 중지하는 쓰기는 따로 커밋한다. 중지가 커밋되지 않아도 다음 410이 다시 중지한다.

**상위 문서:** `payments/retry`의 상위 문서는 경로가 `payments`인 문서다. 관계는 경로로만 정하고 따로 저장하지 않는다. 휴지통 밖 문서의 상위 경로에는 늘 휴지통 밖 문서가 있어야 한다. 그래서 만들기·경로 바꾸기는 없는 상위 문서를 경로의 마지막 이름을 제목으로 한 빈 문서로 만들고, 복원은 휴지통에 있는 상위 문서를 먼저 꺼내고 없으면 만든다. 경로 바꾸기·휴지통 이동은 아래 문서를 함께 옮긴다. 복원은 같은 시각에 함께 휴지통에 들어간 아래 문서를 함께 꺼내고, 영구 삭제는 먼저 따로 휴지통에 넣은 것까지 휴지통에 있는 아래 문서를 모두 함께 지운다. 30일 자동 정리는 문서마다 자기가 휴지통에 들어간 시각부터 세므로, 상위 문서가 만료돼도 그보다 늦게 들어간 아래 문서는 남긴다. 이 쓰기는 여러 문서를 한 트랜잭션에 저장한다. 상위 문서가 없는 문서나 일부만 옮겨진 트리를 남기지 않기 위해서다. 휴지통의 문서를 옮기거나, 자기 아래로 옮기거나, 옮겨 갈 경로 중 하나라도 쓰이고 있거나 경로 한도를 넘으면 아무것도 쓰지 않고 쓰이는 경로를 알린다. 아래에 문서를 두는 쓰기는 휴지통 밖 상위 문서 행을 먼저 잠근다. 그 문서를 옮기거나 휴지통에 넣는 쓰기와 차례로 실행되게 하기 위해서다. 앱은 시작할 때마다 문서가 없는 상위 경로에 소유자 이름으로 빈 문서를 만든다(출처 `system`). 이때도 상위 문서를 먼저 잠근 뒤 그 경로에 여전히 문서가 없고 아래에 휴지통 밖 문서가 있는지 다시 확인한다. 소유자가 쓴 리비전이 없으면 만들지 않는다.

**손그림:** 손그림 다이어그램은 Document 안의 블록 하나(`DrawingBlock`: 블록 ID, SVG 첨부 ID, 장면 첨부 ID, 대체 텍스트)이고 새 루트·BC·마이그레이션이 없다. 장면은 그린 원본이고, 정리한 SVG는 사람과 에이전트가 읽는 모습이다. 둘 다 불변 첨부라 고친 그림은 같은 블록 ID에 새 첨부 쌍을 가리키고, 예전 리비전은 예전 쌍을 그대로 보여 준다. 장면 JSON은 바이트를 고치지 않는다. 대체 텍스트는 한 줄 500자 이하이고 두 첨부는 서로 다른 ID여야 한다. 저장할 때 두 참조를 다른 첨부 참조와 같은 규칙(현재 스페이스 바인딩, 존재)으로 확인하고, SVG 자리는 SVG, 장면 자리는 Excalidraw 장면인지도 확인한다. 한 ID를 어떤 그림의 SVG이면서 다른 그림의 장면으로 쓰지 못한다. 두 ID는 첨부 참조 목록에 함께 들어가므로 이사의 첨부 이동·사본·바인딩, 내보내기, 리비전·블록 복원, 문서 범위 첨부 조회가 이미지와 같은 규칙으로 둘을 다룬다. 댓글은 블록 전체에만 달고 글자 범위 앵커는 거절한다. 검색과 블록 전체 앵커의 인용문은 대체 텍스트만 쓰고 장면 안 글자는 색인하지 않는다. 마크다운에서는 `![대체 텍스트](asset:SVG "excalidraw asset:장면")` 이미지로 쓰고, 캡션이 정확히 이 접두어와 정규 UUID(SVG 자신과 다른 ID)일 때만 그림으로 읽는다. 잘못된 UUID나 근접한 캡션처럼 조금이라도 다르면 오류 없이 일반 이미지로 남는다. 이 예약 캡션을 단 일반 이미지 블록은 어떤 경로로도 만들 수 없고(웹·REST로 보낸 `image` 블록이면 거절), 그림은 `drawing` 블록으로만 만든다. 검사를 거치지 않은 쌍이 마크다운을 거쳐 그림으로 바뀌는 것을 막기 위해서다. 내보낸 읽기용 마크다운을 다시 가져오면 캡션의 장면 참조가 파일 경로로 바뀌어 있어 일반 SVG 이미지로 들어오고 장면은 복원되지 않는다.

**BC 사이:** `workspace` 코어는 `access`를 모른다. `workspace` 입력 어댑터가 `access`의 호출자 모델을 자기 `Access`로 번역한다. 연결 API는 스페이스 ID만 돌려주고, 이름은 화면이 스페이스 목록과 합친다. 업로드 토큰의 형식(`adt_u_<연결 ID>.<비밀>`)은 `access` 모델 `UploadToken`에 있고 두 BC가 함께 읽는다. 연결 ID는 응답에 드러나므로 `workspace` 필터가 먼저 비밀과 연결이 허가와 맞는지 확인해, 틀린 토큰이 그 연결의 요청 제한을 쓰거나 파일을 읽히지 못하게 한다. 통과한 요청은 `access`가 연결 부분으로 호출자와 연결 상태만 판정해 업로드 경로에서만 호출자로 세우고, `workspace`가 허가 행을 잠근 뒤 다시 판정한다. 그래서 서로의 입력 포트를 부르지 않고도 회수·축소가 다음 업로드부터 적용된다. 활동 로그는 365일 보관한다.

오래 열리는 문서 변경 알림(SSE)은 요청을 시작할 때의 인증을 다시 쓰지 않는다. 1초마다 루트 공용 `CurrentCallerUseCase`로 지금의 웹 로그인·연결을 확인하고, `access`가 자기 유스케이스로 확인한 결과를 루트 공용 `CurrentCallerSnapshot`(사용자·로그인·연결 ID·스페이스별 범위와 전역 상한·기술 범위)으로 번역하면 `workspace` 입력 어댑터가 자기 `Access`로 다시 번역한다. 토큰 원문은 요청 동안만 들고 저장·로그·예외 문구에 쓰지 않는다. 회수·축소·로그아웃이나 스페이스 접근 상실이면 스트림을 끝낸다. 문서를 계속 볼 수 있는데 그 문서 스페이스의 권한만 바뀌면 `permission` 신호(새 권한 값)를 보낸다. 문서를 더 볼 수 없거나(`not_found`: 회수, 볼 수 없는 스페이스로 이사, 삭제를 일부러 구분하지 않는다) 로그인이 더는 허용되지 않으면(`unauthenticated`) `revoked` 신호를 보낸 뒤 정상 종료한다. 권한 변경만으로는 문서 버전·리비전이 바뀌지 않는다. 알림은 커밋된 문서 버전·리비전·휴지통·스레드 요약이 바뀌었다는 신호와 권한 값만 담고 본문·제목·스페이스 이름을 담지 않는다. 앱 인스턴스 하나를 전제로 하며 정확히 한 번 전송을 약속하지 않는다. 다시 연결하면 첫 확인에서 다시 알려 최신 조회로 맞춘다.

`webhook`은 활동 로그를 다시 읽어 이벤트를 만든다. 확정 리비전은 실제로 리비전이 늘 때만 원래 작성자와 번호로 남는 `document.revision_confirmed` 항목 하나로 알리고, 자동 저장의 `document.revised`는 그대로 둔다. 댓글 생성은 `createdComment`(댓글 ID와 받은편지함 규칙의 멘션 로그인)가 붙은 항목으로 알린다. 활동 ID는 커밋 전에 정해져 늦게 커밋된 작은 ID가 나중에 보일 수 있으므로, 최근 10분을 5초마다, 가장 오래된 활성 엔드포인트의 등록 시각부터 남아 있는 로그 전체를 1시간마다(시작 1분 뒤 포함) 다시 읽고 유일 키로 한 번만 계획한다. 활동 로그 365일 보관 안에서는 늦은 커밋도 빠뜨리지 않는다. 전달 기록은 원천 활동 ID를 값으로만 가리킨다.

**개인 탐색:** 최근 열람·즐겨찾기는 사용자·문서별 개인 상태로 `workspace`에 두고 루트로 만들지 않는다. 열람은 문서 화면이 명시적으로 기록할 때만 남기고 조회·MCP 읽기는 남기지 않는다. 목록은 지금 볼 수 있는 휴지통 밖 문서만 세고, 영구 삭제한 문서의 개인 상태는 함께 지운다. 백링크는 현재 본문의 실제 문서 링크를 읽어 계산하고(코드·이스케이프·이미지 제외), 볼 수 없는 출처 문서는 개수에도 넣지 않는다. 빠른 메모는 기존 문서 만들기·블록 삽입 쓰기를 그대로 쓰므로 잠금·리비전·`opId` 규칙이 같다.

**P1 경계 선택:** 편집 시간은 같은 문서 협업 시간의 정책이라 새 BC 대신 `workspace`의 독립 루트로 두고 문서 본문에 넣지 않았다. webhook은 구독·전달 기록·재시도라는 자기 상태와 결정 책임이 있어 새 BC로 나눴다. 수정 제안·반응·점유는 열린 스레드 조회와 자식 댓글 상태를 함께 지켜야 해 스레드 안에 두었다. 이사는 중간 상태가 남으면 안 돼 여러 서비스를 연속 호출하지 않고 한 유스케이스가 트랜잭션을 소유한다. SSE는 여러 쓰기 경로에 커밋 후 발행을 끼우는 대신 커밋된 상태를 짧게 조회하고, 백링크는 저장 시 투영·되채움 대신 현재 본문을 읽는다. 둘 다 앱 인스턴스 하나와 지금 규모를 전제로 한 선택이다.

**P2 경계 선택:** 스페이스 멤버십은 권한 메타데이터라 로그인 허용과 요청자 판정을 소유한 `access`의 새 루트로 두고, 마이그레이션은 `V24__create_space_memberships.sql` 하나다. 스페이스는 UUID 값으로만 가리켜 `access`가 `workspace`를 import하지 않고, `workspace` 코어도 `access`를 모른 채 번역된 `Access`만 받는다. `workspace`가 멤버십을 소유하는 안은 로그인 판정이 `workspace`를 불러야 해서, 팀 BC를 새로 만드는 안은 스페이스별 역할 하나를 위해 경계를 늘려서 채택하지 않았다. 손그림은 문서 블록과 불변 첨부 두 개로 표현되므로 새 BC·루트·테이블을 만들지 않았다. 별도 Drawing 루트로 두면 블록 ID·리비전·이사·복원 규칙을 다시 만들어야 하기 때문이다.

### BC 간 연동 요구가 생기면

공개 데이터 계약·모델 번역·변경 책임·판정 시점·실패·재시도·원자성을 먼저 정하고 전달 기술을 선택한다. 각 BC의 유스케이스가 자기 변경·트랜잭션을 소유하는 것이 기본이다. 여러 BC 쓰기의 동시 커밋이 필요하면 분리 전제도 재검토하되 자동 병합하거나 실패를 무시한 연속 호출로 대체하지 않는다.

소비측 코어는 자기 모델·출력 포트를 쓰고 어댑터가 외부 공개 데이터를 번역한다. 인프로세스 어댑터가 상대 입력 포트를 호출하는 구현은 현재 검사에서 실패하므로 필요한 검사 변경과 정상·위반 fixture도 함께 설계한다. 같은 DB·JVM이라는 이유로 상대 테이블에 접근하거나 `config`의 공용 포트·함수 값으로 업무 결합을 숨기지 않는다.

## 패키지 배치

업무 패키지 하나가 BC 하나다. `workspace.documents.domain` 같은 중첩 기능 경로는 금지하며 계층 아래에는 역할·구현 하위 패키지를 둘 수 있다.

```text
<bc>/domain/                         BC 안에서 의미·제약이 같은 공유 값·예외
<bc>/domain/<aggregate>/             루트 하나와 소유 ID·값·엔티티
<bc>/domain/<aggregate>/<helper>/    같은 어그리게이트 내부
<bc>/application/model/              순수 유스케이스 데이터
<bc>/application/port/input/         유스케이스 계약
<bc>/application/port/output/        저장소·외부 기능 계약
<bc>/application/service/            유스케이스 구현
<bc>/adapter/inbound/<group>/        입력 변환, HTTP는 web
<bc>/adapter/outbound/<group>/       외부 구현, Exposed는 persistence
domain/AggregateRoot.kt              공용 기술 표식
config/                             빈 조립·기술 설정
```

- 모든 운영 클래스는 허용 계층 또는 시작 클래스에 둔다. 검사 밖에 새 클래스를 두어 회피하지 않는다.
- 루트 직속 공용 애플리케이션·어댑터는 업무 기능 타입에 의존하지 않는 코드에만 사용한다.

## 의존 규칙

`adapter → application → domain`을 유지한다. 아래의 '자기 BC'에는 허용된 루트 공용 타입도 포함한다. 다른 BC의 모델·입력 계약을 코어에서 직접 참조하지 않는다. 패키지 간 순환도 금지한다.

- `domain`: 언어 타입과 자기 BC 도메인만 사용한다.
- `application/model`: 언어 타입·자기 BC 도메인·모델만 사용한다. 포트는 모델을 참조할 수 있고 모델은 포트를 참조하지 않는다.
- 입력·출력 포트: 언어 타입·자기 BC 도메인·모델·포트만 사용한다. Spring·Exposed·HTTP·서비스 구현·어댑터·설정을 참조하지 않는다.
- `application/service`: 자기 BC의 도메인·애플리케이션을 사용한다. Spring 타입은 **`org.springframework.transaction.annotation`의 `Transactional`·`Propagation`·`Isolation`만** 허용한다.
- 입력 어댑터: 자기 BC 입력 포트·도메인·모델과 입력 기술을 사용한다. 출력 어댑터: 자기 BC 출력 포트·도메인·모델과 외부 기술을 사용한다. 서비스 구현·반대 방향 포트·다른 어댑터 그룹·`config`를 직접 참조하지 않는다.
- Exposed·Spring JDBC·`java.sql`·`javax.sql`은 출력 어댑터의 `persistence` 경로와 `config`에서만 사용한다. Exposed 행·테이블·쿼리·트랜잭션 타입을 포트·도메인·웹 요청/응답으로 노출하지 않고 어댑터 안에서 변환한다.
- `config`는 모든 BC 구현의 조립과 기술 설정에 접근할 수 있지만 금지된 업무 호출을 만들지 않는다.

코어의 직접 I/O는 금지한다. 대상은 `java.io`, `java.sql`, `javax.sql`, `java.net`, `java.nio.file`, `java.nio.channels`, `java.rmi`, `java.util.prefs`, `kotlin.io`와 `Process`·`ProcessBuilder`·`ProcessHandle`·`Runtime`이다. 예외는 순수 계약 `java.io.Serializable`과 주소 값 `java.net.URI`뿐이다. 파일·네트워크·DB·외부 프로세스는 출력 포트로 요청한다.

### 역할과 위치

- 컨트롤러와 합성 컨트롤러 애너테이션은 입력 어댑터의 `*Controller`, `@Configuration`은 `config`의 `*Config`에 둔다. 시작 클래스의 `@SpringBootApplication`은 예외다.
- 입력 포트 구현은 자기 BC 서비스, 출력 포트·`*Repository` 구현은 자기 BC 출력 어댑터에 둔다. 보조 서비스에 포트 구현을 강제하지 않는다.
- 포트 역할의 전체 경로는 구현 경로에 **연속된 완전한 세그먼트**로 들어가야 한다. `port/output/payment/refund`는 `adapter/outbound/stripe/payment/refund` 또는 `adapter/outbound/payment/refund/stripe`에서 구현한다. 하위 역할이 없는 포트는 자기 기능의 해당 구현 계층에 둔다. 루트 공용 포트는 기능별 구현에서 사용할 수 있다. 입력 어댑터가 호출하는 입력 포트에도 역할 경로를 맞춘다.
- 어댑터 격리 단위는 **BC + 방향 + 첫 그룹**이다. `outbound/stripe/...`와 `outbound/paypal/...`은 격리되고 같은 그룹의 하위 패키지는 함께 쓸 수 있다. 공급자 격리는 첫 그룹으로 표현한다.
- 포트 패키지의 `UseCase`·`Repository`·`Port`·`Source`·`Catalog`·`Reporter`·`Gateway`·`Verifier`·`Store`·`Lookup`·`Classifier` 접미사는 인터페이스에 쓴다. `Command`·`Result`와 입력 포트의 예외 타입은 순수 데이터 계약으로 둘 수 있다.

### 어그리게이트 규칙

- 루트에 `@AggregateRoot`를 붙이고 `<bc>.domain.<aggregate>` 바로 아래에 하나만 둔다. BC의 `domain` 바로 아래나 루트의 하위 패키지에 새 루트를 두지 않는다.
- 생성자·생성된 `copy`는 비공개, 프로퍼티는 `val`로 유지하고 생성·복원·상태 전이를 구분한다. 보관한 컬렉션·요소의 외부 변경도 검토한다.
- 도메인은 다른 어그리게이트의 루트 객체 대신 의미가 맞는 ID·불변 값을 참조한다. 자기 루트는 내부 하위 패키지에서 참조할 수 있다. 자기 BC 애플리케이션·어댑터와 `config`는 루트를 사용하고 서비스는 여러 저장소를 호출할 수 있다.
- 루트를 다루는 출력 포트는 이름과 무관하게 저장소다. **포트 하나의 루트는 최대 하나, 루트 하나의 출력 포트도 최대 하나**이며 상속·제네릭에도 적용한다. 루트를 노출하지 않는 조회용 `Store`는 별도 계약이다.

### BC 경계

- `HexagonalArchitectureTest.contextAggregates`에 `workspace → space.Space, document.Document, thread.CommentThread, inbox.InboxItem, asset.Asset, upload.UploadGrant, editsession.EditSession`, `webhook → endpoint.WebhookEndpoint, delivery.WebhookDelivery`, `access → user.User, connection.Connection, client.OAuthClient, authorization.AuthorizationRequest, session.WebSession, emergency.EmergencyLoginGrant, membership.SpaceMembership`를 유지하고 새 BC·루트를 같은 변경에서 등록한다.
- 미등록 업무 패키지·루트, 코드 없는 등록 항목, 중첩 기능 경로를 만들지 않는다.
- 루트 공용 도메인에는 `AggregateRoot`만 둔다. BC 안의 공유 값도 의미·제약이 같은 경우에만 올린다.
- 자기 저장소·테이블을 사용하고 다른 BC 타입을 직접 참조하지 않는다. `config`의 조립만 예외로 둔다.
- 어댑터의 다른 BC 모델 참조처럼 검사에 잡히지 않는 결합도 검토한다. 새 연동은 [별도 계약](#bc-간-연동-요구가-생기면)을 설계한다.

## 의존성 주입과 빈 조립

- 운영 의존성은 생성자 `private val`로 받는다. 필드·세터·메서드의 `@Autowired`·`@Inject`·`@Resource`·`@Value` 주입은 금지한다.
- 유스케이스에 `@Service`·`@Component`를 붙이지 않고 `config`의 `@Bean`으로 조립한다.
- 테스트 프레임워크 주입은 [테스트 예외](code-quality.md#테스트-코드의-차이)를 따른다.

## 트랜잭션

- 유스케이스의 Spring `@Transactional`로 업무 단위를 정하고 어그리게이트에서 불변식을 지킨다.
- Exposed Spring Boot 4 스타터의 `springTransactionManager`를 사용한다. `Database`·매니저를 중복 구성하지 않고 저장소에 별도 `transaction {}`를 넣지 않는다.
- 유스케이스에 `TransactionTemplate`·매니저를 주입하거나 공통 트랜잭션 추상화·데코레이터를 추가하지 않는다.
- 서비스는 `@Transactional(readOnly = true)`를 기본으로 쓰고 쓰기 메서드에서 재정의한다. 문서·스레드·연결 변경의 행 잠금·조회·저장도 서비스 쓰기 트랜잭션 안에서 수행한다. 기본 `REQUIRED`의 기존 트랜잭션 참여 범위도 확인한다.
- Spring이 관리하는 빈을 외부에서 호출한다. 직접 생성한 객체나 자기 객체 내부 호출을 새 트랜잭션 경계로 취급하지 않는다. `readOnly`를 접근 제어나 쓰기 차단에 쓰지 않는다.
- 기본 롤백 대상은 `RuntimeException`과 `Error`다. 그 밖의 예외도 롤백해야 한다면 `rollbackFor`를 명시한다.
- 가상 스레드에서도 JDBC 트랜잭션 안에서 비동기·코루틴 디스패처 전환으로 작업을 넘기지 않는다. 가상 스레드를 이유로 연결 풀 제한을 없애지 않고 트래픽·쿼리에 맞게 조정한다.
- 모든 입력·출력 어댑터의 클래스·메서드는 직접·합성·상속 `@Transactional`, 트랜잭션 인프라 의존, 수동 트랜잭션 제어를 금지한다. 연결·커넥터 경유나 메서드 참조도 같다. 일반 저장소 조회는 허용한다. 정확한 탐지 대상과 JTA 도입 조건은 [트랜잭션 검사](quality-maintenance.md#트랜잭션-검사-확장)에 있다.
- 문서 변경과 그 변경이 확정하는 리비전은 함께 커밋·롤백하며 여러 루트의 원자적 쓰기는 위 분류 절차에서 먼저 재검토한다.

## 자동 검사와 완료 조건

- 선택 근거·BC와 루트 등록·[기본 범위](development.md#테스트-범위)의 불변식과 실패 경로 테스트를 남기고 [전체 빌드](development.md#실행과-검증)를 통과한다.
- 공통·DDD·BC 검사를 운영 코드에 함께 적용한다.
- 정적 검사 통과만으로 업무 의미·깊은 불변성·조립 내용·실제 변경 대상을 보장한다고 보고하지 않는다.
- 누락된 루트 표식, 함수 값·반사·인라인·값 클래스 소거를 통한 결합은 코드 검토와 행동 테스트로 확인한다. 요구에 없는 사업 결정을 추측하지 않는다.
